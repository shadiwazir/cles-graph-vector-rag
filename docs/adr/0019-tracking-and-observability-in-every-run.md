# 0019. MLflow, DVC and observability are part of every run [ob.3]

**Status:** accepted (user direction, 2026-11-14)

**Context.** The tools were requested to measure, compare and evaluate progress, and the project is a PoC that will never be released. Until now they existed but sat beside the workflow: MLflow only logged training runs (on a GPU machine's own SQLite file), telemetry was off by default, evaluation results lived in report files, and DVC tracked only the raw data and datasets.

**Decision.** The tools are wired into the normal workflow as best-effort hooks that never break a run.
1. **MLflow:** every stage run becomes a run in the experiment `cles-pipeline` (summary numbers as metrics, git commit and DVC hashes as tags, `git_dirty` flag), from `stage_main`. Each evaluated system becomes a run in `cles-eval`; training stays in `cles-sft`. GPU machines track into SQLite; `cles.mlflow_import` copies those runs into the server and registers adapters in the model registry (`cles-advisor`). The server runs with proxied artifact storage and the same version as the client. Tests set `MLFLOW_ENABLED=false`.
2. **Observability:** the pipeline script starts the whole stack (`infra`) and turns telemetry on whenever the Collector answers. Stage summaries become gauges (`cles_stage_value`), evaluation scores become gauges (`cles_eval_quality`, `cles_eval_count`), drift violations a gauge. A second Grafana dashboard shows model quality per system, progress per evaluation run and pipeline cost. Alert rules (online quality, pipeline health, offline quality, drift) are Prometheus rules with unit tests (`promtool`, `scripts/pipeline.sh alerts-test`).
3. **DVC:** the pipeline snapshots (`dvc add` and `push`) after the step that produces data: the extraction export (new stage `export_extractions`, JSONL, stable order), datasets, evaluation outputs and adapters. `build_manifest.extraction_hash` records the export hash. `metrics/eval.json` is git-tracked and listed in `dvc.yaml`, so `dvc metrics diff <rev>` compares evaluations between commits.
4. **Evaluation loop:** the judge, label capture (explorer, blind mode) and calibration stage from INSTRUCTIONS 19; `drift_check` compares the latest evaluation with `eval/baseline.json` and live traffic (audit rows with `environment = 'live'`) with the evaluation reference; the lawyer's verdict is stored through `POST /feedback`.

**Options considered.** (a) Keep the tools for a later phase: rejected, they would never be used. (b) Make MLflow mandatory for every stage: rejected, a stopped server must not stop the work (the check costs about two seconds). (c) One MLflow run per pipeline invocation instead of per stage: rejected, per-stage runs compare directly (cost, duration, counts per stage). (d) Dashboards reading MLflow: Grafana cannot read MLflow, so evaluation scores are also emitted as OpenTelemetry gauges.

**Consequences.** Statistical power is small (48 evaluation examples, little traffic): thresholds in `eval/thresholds.yaml` and `alerts.yml` are placeholders and the drift and alert checks prove the mechanics, not production fitness. No Alertmanager receiver is configured, so alerts appear in Prometheus and in Grafana only. The judge is not calibrated until lawyer labels exist (at least 30 labelled answers and kappa >= 0.6). Batch metrics persist in Prometheus because the Collector keeps them for 60 minutes after the stage exits. Test and smoke requests carry `environment = 'test'` so they do not count as traffic.
